## Zexo CSS 加载机制分析与 CDN 架构讨论

- 摸清加载机制：Worker（index.js）服务端拼 HTML，所有前端资产（CSS+JS 约 20+ 文件）均以 `<link>`/`<script>` 外链 `cdn.jsdelivr.net/gh/Zarijaden/Zexo/src/*`；head 固定加载 font/admin_all_{light|dark}/zexo_theme/md_editor.css，页面级样式由各路由写入 `zexo_js` 变量拼入 body 末尾（zexo_dash_foot）；主题二选一由 KV 的 `zexo_theme_mode` 服务端决定，body 输出 `dark-edition` class。
- 关键结论：gulp 的 dist/*.css 是死代码（页面引用 src/ 未压缩版，dist 仅用于 small_white_mouse_update 自更新 Worker）；jsDelivr gh 链接未锁版本，缓存最长约 12h。
- 用户立场（重要）：明确想"直接改基座"（admin_all/login/install/error），走自己的设计路线，认为覆盖层（zexo_theme.css）不优雅；痛点集中在 jsDelivr 缓存不可控与国内访问不稳定。已向其确认：改基座无问题，唯一注意点是 admin_all_light/dark 双文件需同步维护，建议合并为单文件 + CSS 变量 + `body.dark-edition` 钩子（该 class 钩子已存在）。
- 待用户决策的选项：① jsDelivr purge（手动 purge.jsdelivr.net 或 GitHub Actions 自动 purge，项目已有 dev-gulp.yml 可搭车）；② 资产迁移候选：Cloudflare Pages / GitHub Pages / raw.githack / statically；③ Workers Assets/KV 自托管（架构最干净，顺带解决 URL 硬编码 Zarijaden/Zexo 导致 fork 部署前端全挂的问题——该硬编码波及全部 JS 不只是样式）。
